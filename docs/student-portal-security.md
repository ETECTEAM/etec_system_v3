# Student Portal — security review and login plan

Status: **analysis only. Nothing in this document is implemented.** Findings come from reading
the code; none were reproduced against a running server.

Scope: how a student proves who they are (`students.attendance_code`), what that code unlocks,
and how to add a second factor (authenticator app or one-time code) before the portal launches.

---

## 1. How it works today

| Piece | Where | Notes |
|---|---|---|
| Student code | `students.attendance_code`, format `XXXX-XXXX` | Generated by `StudentRegistrationService::uniqueAttendanceCode()` from `Str::random(4)` uppercased, so about 36 characters per position (roughly 2.8 × 10¹² possibilities). It is an identifier, not a secret. |
| Portal login | `StudentPortalController::authenticate` | The code is the **only** credential. On success it stores `student_portal_id` in the session. |
| Portal data | `StudentPortalController::dashboard` | Name, gender, phone, email, classes, instructor, room, full attendance history. |
| QR attendance | `AttendanceQrService` | The same code identifies a student on the public QR check-in form. |
| Forgot code | `sendForgotCode` / `storeRecoveryEmailSetup` | Portal email (`name@etec.com`) → new code sent to the recovery email. |
| Instructor view | `AttendanceRecord.vue` | Shows each student's code with a copy button (added so instructors can hand it out). |
| Public link | `/student-attendance/{public_token}` | 40-character random token per enrollment; read-only attendance summary. |

Where the code is already known to other people: instructors (roster), the student's recovery
email, and everyone who watches them use the QR form. Treat it like a username.

## 2. Findings (highest risk first)

### F1 — Anyone can take over a student's code through "forgot code"  · High

`sendForgotCode` looks a student up by **portal email only**. That email is predictable:
`StudentRegistrationService::uniqueStudentEmail()` builds it from the student's name
(`roeung.bunchhorng@etec.com`). If the student has **no recovery email**, the flow continues to
`storeRecoveryEmailSetup`, which:

1. saves whatever recovery email the requester types,
2. generates a **new** attendance code and mails it to that address,
3. **replaces** the student's real code.

Nothing proves the requester is the student. The whole chain is unauthenticated (rate limit
`throttle:5,1` per IP only).

Who is exposed: every student without a recovery email. That includes **all students created by
the Legacy CSV import** (`createStudent` is called without an email) and manually registered ones.

Effect: an attacker who knows a student's name can lock the real student out and receive the
portal login and QR-attendance identity. This also defeats a second factor whenever the second
factor can be reset through the same flow.

Fix direction: setting or changing a recovery email must require proof of identity that an
outsider cannot get from a name. Options: only while signed in to the portal; via a single-use,
expiring setup link issued by an admin or the class instructor; or after verifying the phone
number on file.

### F2 — Public attendance by numeric enrollment ID  · High

`GET /attendance/{enrollment}` (`routes/web/frontend/attendance.php`, `showById`) needs no token.
Trying `/attendance/1`, `/2`, `/3` … returns each student's name, gender, class and attendance
records. The only protection is `throttle:60,1` per IP. Nothing in the frontend references it.

Fix: remove the route. `/student-attendance/{public_token}` covers the real use case.

### F3 — Portal login is a single factor  · Medium (by design until launch)

Anyone who has seen a student's code can log in and read that student's data. This is the case
the second factor in section 3 is meant to close.

### F4 — Login rate limit is keyed on IP + code  · Low

`authenticate` uses `student-portal:{ip}|{code}` with 5 tries per minute. Trying many *different*
codes from one IP never hits that key; only the route-level `throttle:10,1` limits it. Guessing
is impractical at this code size, but the per-code limit does not protect a single student from
distributed attempts. Limit per student and per IP separately, with lockout and logging.

### F5 — Instructors can see the code  · Info

Fine once login needs a second factor. If the portal launches with code-only login, hide the
code from instructors (or reveal on click and log it).

## 3. Target design: code + second factor

The code becomes the **identifier**. The second factor is the credential. The safe part is how
the second factor is **first set up**.

```
Instructor/admin issues a one-time setup link  →  student opens it
      →  student enrols the second factor       →  from then on: code + factor at every login
```

Do **not** enrol the factor on a first code-only login: whoever knows the code would enrol first.

### Option A — Authenticator app (TOTP)

- Library: e.g. `pragmarx/google2fa` (or `spomky-labs/otphp`); QR shown at setup.
- Store the secret encrypted (`Crypt` / `encrypted` cast). Add `totp_confirmed_at`.
- Generate 8–10 single-use **backup codes**, hashed.
- Needs students to have and understand an authenticator app.

### Option B — One-time code by email or Telegram

- Reuse the existing OTP infrastructure (`OtpVerification`, `TelegramService`).
- Login: code → system sends a 6-digit OTP to the verified recovery email or Telegram → student enters it.
- No app to install, no secret to store. Depends on the recovery channel being verified first.

| | A: TOTP | B: Email/Telegram OTP |
|---|---|---|
| Student effort | Install app, scan QR | None beyond receiving a message |
| Works offline | Yes | No |
| Build effort | Medium (secret storage, backup codes) | Low–medium (infra exists) |
| Recovery | Backup codes / admin reset | Change verified channel |

Suggested default: **B** unless the client specifically wants an authenticator app.

## 4. Plan

**Phase 1 — close the holes (do first, independent of 2FA)**

1. Remove `GET /attendance/{enrollment}` and `showById`. Search for links to it first.
2. Lock down `storeRecoveryEmailSetup`: require identity proof (section 2, F1). Never replace the
   code in the same request that sets an unverified email.
3. Change the login limiter to per-student plus per-IP; log failures.
4. Add tests: unauthenticated recovery-email setup must fail; by-ID route returns 404.

**Phase 2 — second factor**

1. Migration: second-factor columns (or a separate table), backup codes.
2. Setup flow: instructor/admin "issue setup link" (single-use, expires in minutes/hours).
3. Login: code → factor challenge → set `student_portal_id` only after both pass.
4. Recovery and admin reset (audited).
5. Session: regenerate on success, short lifetime, log out button.

**Phase 3 — data and rollout**

1. Backfill: existing students have no factor; portal stays closed until the setup link is used.
2. Decide the client policy (who may hand out codes and setup links).
3. Update `docs/` and this file when done.

---

## 5. Test checklist

- [ ] Correct code, no factor → cannot reach `/student-portal`.
- [ ] Correct code + wrong factor 5× → locked for that student, other IPs also blocked.
- [ ] Setup link works once, then 404; expired link fails.
- [ ] Forgot-code without proof of identity does **not** change any recovery email or code.
- [ ] `/attendance/1` (by ID) returns 404.
- [ ] Legacy-CSV-imported student (no recovery email) cannot be taken over by name.
- [ ] Session is regenerated at login and cleared at logout.

---

## 6. Decisions needed from the client / owner

1. Second factor: authenticator app (A) or email/Telegram one-time code (B)?
2. Who issues the first-time setup link: instructor, admin, or both?
3. Are students allowed to see the portal at all before the factor is enrolled? (Recommended: no.)
4. Should instructors keep seeing the code once login needs a second factor?
